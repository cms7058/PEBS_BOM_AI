# 产品架构与下一步行动

> 日期：2026-04-28
> 上下文：PEBS_BOM 已存在并实现了 3D→BOM 引擎；曾考虑独立做 PEBS_Bom_AI；最终决定**合并到 PEBS_BOM**，以 skill 架构演进

## 一、核心决策：以 PEBS_BOM 为主项目，skill 化演进

放弃独立做 PEBS_Bom_AI 项目。理由：
- PEBS_BOM 已有完整的 3D→BOM + 可视化 + Agent 操控 + 编辑历史，是 60-70% 完成的产品
- 重新建一个项目等于浪费已有资产
- "skill 架构"是 AI Agent 时代的合适形态，不是 2015 年的 SaaS 平台

## 二、四层架构

```
┌──────────────────────────────────────────────────────┐
│  Layer 3：开放 / 第三方 skill（年 ARR 1000 万后再考虑） │
└──────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────┐
│  Layer 2：你自己的 skill 集（按客户需求拉动加）        │
│  采购流程 / 项目任务 / 设计 TODO / 供应链分析 / ...   │
│  每个 skill 必须满足：客户主动要 3 次以上才加         │
└──────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────┐
│  Layer 1：核心钩子（必须比 Excel 好 10 倍）            │
│  BOM 智能管理 + AI 选型映射 + 客户历史风险预警        │
│  → 这是工程师每天打开它的"唯一理由"                  │
└──────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────┐
│  Layer 0：引擎（PEBS_BOM 已有）                       │
│  3D → BOM 提取                                        │
└──────────────────────────────────────────────────────┘
```

**第一条核心原则**：Layer 1 必须**单点深到极致**，没有 Layer 1 的"必须每天用"理由，上面所有 skill 都是空中楼阁。

**第二条核心原则**：Layer 2 的 skill **不是创始人定的，是客户拉出来的**。客户连续 3 次以上抱怨"要是能 X 就好了"，才动手做 X。

## 四、Layer 1 补完计划（接下来 4-6 周）

### P0：SKU 智能映射的雏形（1-2 周）
详见 [04-SKU智能映射设计.md](04-SKU智能映射设计.md)

即使无外部供应商 API，光做"公司内部 SKU 一致性"也极有价值。

### P0：客户历史数据沉淀（2 周）
每次项目完成 → 把这次 BOM 数据沉淀到"公司知识库"。第二次新建 BOM 时：
- "这个件公司用过 5 次"
- "上次单价 ¥X、货期 Y 天"（数据来自客户自己上传）
- "去年同类项目 BOM 总价 ¥XXX，本项目比之前贵 12%"

**为什么必须做**：这是无 API 路线下**最关键的差异化** —— 客户用得越久越离不开。

### P1：风险预警 skill（1 周）
基于规则的轻版：
- 无历史数据的件 → 黄色提示
- 单源件 → 红色提示
- custom / 非标件 → 红色提示
- 长货期件（结合客户历史）→ 黄色提示

### P1：BOM ECO 变更影响分析（1 周）
- "这个零件改了，下游受影响的 5 个工序：xxx"
- 非标行业的真痛点，纯软件能力不依赖外部数据
