# SKU 智能映射设计

> 日期：2026-04-28
> 优先级：P0（Layer 1 核心钩子）
> 关联：[03-产品架构与下一步.md](03-产品架构与下一步.md)

## 一、什么是 SKU 智能映射

**SKU**（Stock Keeping Unit）= 一个零件唯一的"身份证号"。

**SKU 映射** = 把工程师乱写的零件名/型号 → 对应到一个**标准化的、唯一的、可被下游识别的编码**。

## 二、痛点场景

工程师在 SolidWorks 中对同一类直线导轨可能写：

```
HG25_导轨_左
HG-25 直线导轨 加长版
HIWIN HG25CA  L=1500
hg25 滑块导轨组 (含2滑块)
直线导轨HG25 L=1.5m
台湾上银 HGW25CC
```

这 6 行其实是 2-3 个真实的物料，但因为命名乱：

| 下游环节 | 损失 |
|---|---|
| **采购** | 当成 6 个不同件去询价；或合并错了，到货装不上 |
| **库存** | 同一件多个编码占位，账目对不上 |
| **ERP** | 录入时手动建新编码，半年后系统里有几千个"僵尸 SKU" |
| **历史数据** | "我们公司过去 2 年用过多少 HG25" 根本查不出来 |
| **报价** | 新项目想复用上次 BOM，搜不到 |

**这是为什么 BOM 工具光"导出表格"是不够的** —— 不解决映射，BOM 数据是"死"的，所有下游价值打 5 折。

## 三、目标效果

```
原始名                        →  标准化 SKU         供应商    备注
─────────────────────────────────────────────────────────────────
HG25_导轨_左                  →  HIWIN-HG25CA      上银     标准款
HG-25 直线导轨 加长版          →  HIWIN-HG25CA-L1500 上银    L=1500 加长
HIWIN HG25CA  L=1500          →  HIWIN-HG25CA-L1500 上银    重复识别
hg25 滑块导轨组 (含2滑块)      →  HIWIN-HG25CA-2BLK  上银     双滑块套件
直线导轨HG25 L=1.5m           →  HIWIN-HG25CA-L1500 上银    重复识别
台湾上银 HGW25CC              →  HIWIN-HGW25CC      上银     法兰款（不是 HG25）
```

工程师前端体验：
- 上传 BOM → 系统识别 "你这 6 行其实是 4 个独立 SKU + 2 处重复"
- 弹窗确认（"系统认为这两行是同一件，对吗？"）
- 确认后写进数据库，**之后所有项目都按统一 SKU 检索**

## 四、为什么 LLM 比纯规则强

**纯规则**：写正则、维护字典。直线导轨能 cover，但伺服电机、气缸、传感器各自要写一套规则。工程师写 "M4×10" / "M4*10" / "M4 螺钉 长 10mm" / "M4-10 GB/T70"，**正则永远有漏网**。

**LLM 加持**：
- 理解语义："这个写法是直线导轨"、"上银 = HIWIN"
- 配合公司**历史数据**：你公司过去用过的所有 SKU + 工程师命名习惯 → 越用越准
- 配合**供应商型号库**：米思米/怡合达/上银的标准型号表（即使没 API，离线静态目录也能用）

## 五、三层价值（由浅到深）

### 第一层：内部一致性（必做，工作量小，价值大）
公司内部建立"主数据"。同一件无论谁画图都映射到同一个 SKU。
- 不依赖任何外部 API
- 1-2 周能做出雏形
- 直接解决 "BOM 数据是死的" 问题

### 第二层：对接外部标准型号（中等工作量）
把内部 SKU 关联到米思米/怡合达/上银/SKF 的**标准型号目录**（公开 PDF / 网站，可以爬一次性入库）。
- 工程师选型时能看到 "对应米思米型号 XXX"
- 即使没有实时价格，**型号是确定的**

### 第三层：对接实时数据（依赖 API）
SKU 映射通了之后，比价 / 库存 / 货期才能挂上去。

**没有第一层和第二层做底，第三层就是空中楼阁** —— 这是为什么即使 API 全军覆没，SKU 智能映射本身就是核心钩子。

## 七、实施路径

### MVP（1-2 周）
1. 数据模型：`Part` 表 + `PartAlias` 表（一个 SKU 多个别名）
2. 工程师上传 BOM 时，自动检索：这个零件名在历史里出现过吗？
3. **没出现过** → 让工程师手动建 SKU + 选品类 + 填关键参数（型号、品牌、规格）
4. **出现过** → 自动套用，弹窗确认
5. **公司维度**沉淀（不是用户维度）—— 工程师 A 建的 SKU，工程师 B 下次自动复用

### V1（再 2-3 周）
1. 接入 LLM：用户写 "M4×10 螺钉" → LLM 给 "GB/T 70.1 M4×10 内六角圆柱头" 标准命名建议
2. 内置常见品类的"标准目录"种子数据：直线导轨、伺服电机、气缸、传感器、紧固件 5 大类
3. 模糊匹配：写 "HIWIN" 自动匹配 "上银"、写 "HG-25" 自动匹配 "HG25"

### V2（等数据通路确定）
对接立创 / 京东工业 / 米思米的 SKU 主数据，把内部 SKU 关联到外部供应商真实编码。

## 八、数据模型草案（待细化）

```python
# Part - 公司主数据
class Part:
    id: int
    sku_internal: str            # 公司内部唯一编码，如 "PRT-2026-00123"
    name_standard: str           # 标准名，如 "HIWIN-HG25CA-L1500"
    category: str                # 品类，如 "直线导轨"
    brand: str                   # 品牌，如 "上银"
    spec: dict                   # 关键参数 {型号, 长度, 滑块数, ...}
    sku_external: dict           # 外部供应商 SKU {misumi: "...", lcsc: "...", jd: "..."}
    created_by: int              # 创建工程师
    created_at: datetime

# PartAlias - 工程师写法 → Part 的映射
class PartAlias:
    id: int
    part_id: int                 # FK to Part
    raw_name: str                # 工程师在 CAD 里的原始命名
    confidence: float            # 系统判定置信度 (0-1)
    confirmed_by: int            # 确认人
    confirmed_at: datetime
```
